## v0.2.1

- **RPC refusals no longer stop a deposit (first real-mainnet bug report).** The user's first live run failed before signing with `403 Access forbidden` from `api.mainnet-beta.solana.com`: that public server refuses requests from browser extensions. Nothing was signed or sent. All Solana calls (Alias pages, background, and the Privacy Cash SDK's own calls) now go through one fallback fetch: your own RPC from Settings first, then PublicNode, OnFinality public, `api.mainnet.solana.com`, `api.mainnet-beta.solana.com`. 401/403/404/405/429/5xx or a network error moves to the next server; the last working one is remembered. Settings gains "Your own RPC (optional)" (https only). — Automated-tested (skip on 403/429/network error, stickiness, custom-first, a real web3.js `getBalance` through the fallback), Manual-Chromium-tested (first server answers 403 exactly like the user's; the deposit reaches the next server). Whether each public server accepts Alias in real Chrome: not verifiable from here; a Helius URL in Settings is the dependable route.

- **Funding page never spins silently.** It now mirrors the Alias window: the current step, SDK progress lines (pool scan, proving), the real error if a step fails, and "Done" at the end. — Manual-Chromium-tested (error case shown on the funding page).
- **First-funding pool scan.** Root cause of a long "building the private deposit" wait: before the first deposit the SDK downloads the pool's entire history (20,000 outputs per request) and trial-decrypts each to find funds the alias already owns. Alias now starts that scan at the pool's current end when the alias provably owns nothing there: the vault's 12 words were generated by this install (recorded as `vault.origin = created`) and no operation of that alias ever reached the pool. Imported phrases and vaults of unknown origin keep the full scan. The storage key is checked against the SDK's own constant in a test. — Automated-tested (rule, key, fallback when the pool size is unavailable), Manual-Chromium-tested (offset set to the mocked pool size).
- **Proving verified in the real extension context.** A valid deposit proof input (dummy inputs, as in a fresh deposit) proves in Node in 5.2 s and inside an extension page in Chromium in 9.5 s, single-threaded, 2 cores. So proving works under MV3's CSP and is not a hang risk. — Real proof, no network needed (`scripts/make-proof-input.mjs`).

## v0.2.0

- **Privacy audit of the funding path (privacycash SDK v1.2.3 source).** Deposit transaction accounts: pool tree, nullifier PDAs, pool token account, global config, fee recipient, the signer (main wallet), System Program. The alias address is not in it. Scanning downloads all encrypted outputs by index range and sends no address. Withdrawal is submitted by the relayer with recipient = alias. Result: no account on chain names both wallets. — Verified by source inspection.
  - Remaining leak 1, **timing and amount**: a deposit and a near-identical payout minutes apart are easy to match. Addressed below.
  - Remaining leak 2, **the relayer operator**: it receives the deposit (sender = main wallet) and the withdrawal (recipient = alias), from the same browser/IP. It could link them off-chain. Not fixable in the extension; disclosed in the README.
- **Payout timing split**: Fund and Return now ask when the pool pays out: Right away / In 1 hour / Tomorrow. Delayed payouts wait in the pool (owned by the alias's shielded key), are journaled with `payAfter`, get a toolbar badge via `chrome.alarms` when due, and show on Home as "waiting in the pool" with Pay now. Only these three delays are accepted. The operation window stops its keep-alive while waiting so the vault still auto-locks. — Automated-tested (delay validation, journaling, explicit pay-now reopen), Manual-Chromium-tested (choice + explanation, Home card, ops window waiting without submitting; the confirmed deposit is a labeled FIXTURE with mocked RPC).
- **Return without pasting**: the main wallet that last funded through Alias (with its wallet name) is the default destination; "Change" reveals the address field. — Manual-Chromium-tested.
- **Fresh alias per unknown site, for real**: the connect window previously said "fresh alias" but preselected Trading. Unknown sites now get a new alias named after the site, created only when you approve; recognized sites without a matching alias get one of the right kind. — Manual-Chromium-tested (dapp receives an address different from Trading Alias).
- **Home with many aliases**: pills wrap, cap at 3 + "All n" + "＋ New"; a paginated "Your aliases" screen (5 per page). Fixes "＋ New" being clipped. — Manual-Chromium-tested with 6 aliases.
- UI copy: em dashes removed from screens.

## Completed (v0.1.0)

### Vault and keys
- Encrypted vault: BIP39 mnemonic, AES-256-GCM at rest, PBKDF2-SHA256 600k iterations; unlocked seed only in `chrome.storage.session`. — Implemented, Automated-tested (plaintext never at rest; wrong password rejected), Manual-Chromium-tested (lock/unlock round trip).
- Alias keys derived m/44'/501'/i'/0', never persisted; identical after restart and after phrase restore. — Automated-tested.
- Recovery: 12-word phrase shown once at setup, re-revealable with password; import restores the same addresses. — Automated-tested, Manual-Chromium-tested (onboarding).

### Wallet Standard
- Alias registers as a genuine Wallet Standard wallet (standard:connect/disconnect/events, solana:signTransaction/signAndSendTransaction/signMessage). — Manual-Chromium-tested: a test dapp page discovered "Alias", connected through the real wallet picker protocol, and received the alias address.
- Discovery of jup.ag's picker specifically: not run here (needs live jup.ag). The protocol used is the same one Jupiter's wallet list consumes. — Remaining acceptance step.

### Privacy firewall / identity routing
- Exact-origin grants (scheme+host+port), scoped by network; lookalike origins (`jup.ag.evil.com`, `sub.jup.ag`, `http://jup.ag`) get nothing. — Automated-tested.
- Connection approval window triggered by a real connection request, naming the exact website, with a recommendation (Trading for recognized trading origins, fresh alias for unknown sites) and "Choose another". — Manual-Chromium-tested with screenshot.
- Signing policy: unconnected origins rejected; transactions not signed by the connected alias rejected; mismatched account rejected; every signature behind an approval window; closing the window = rejection; declined approval = no signature. — Automated-tested.
- Mainnet consent: explicit checkbox + settings flag; per-transaction and per-operation SOL limits; on mainnet, a transaction whose effects cannot be simulated cannot be approved. — Automated-tested (consent + limits), Manual-Chromium-tested (consent UI). Simulation against live RPC: not run here.

### Private funding and return (Privacy Cash)
- Real `privacycash` SDK v1.2.3 (pinned), low-level `deposit`/`withdraw`/`getUtxos`/`getConfig`; shielded account derived from the alias key, so the alias owns pooled funds; the main wallet only ever signs its own deposit. — Implemented.
- Circuit files (`transaction2.wasm/.zkey`) bundled from the SDK with SHA-256 manifest, verified at runtime before any operation. — Manual-Chromium-tested (verification step shown passing in the ops window).
- External-wallet deposit signature verification: byte-identical message check + ed25519 verify + fee-payer check before relaying. — Automated-tested (swapped transaction, wrong signer, forged signature all rejected).
- Companion funding page: Wallet Standard discovery of installed external wallets (never listing Alias itself), connect, sign, report back over the extension bridge; actionable failure states. — Manual-Chromium-tested with a mock main wallet (labeled): pick-wallet handshake and progress reporting worked end to end in real Chromium.
- Operation journal: encrypted with a seed-derived key, written before submission; unknown stays unknown; recheck after restart verifies on chain and never resends; resume skips completed legs. — Automated-tested (journal), Manual-Chromium-tested (history + honest failure path when the network is unreachable).
- Live fees/minimums fetched from the relayer config before accepting an amount; fee + net estimate shown. — Implemented; fee math Automated-tested against the SDK's own formula; shown in Chromium with a mocked relayer config (labeled).

### UI
- 360×560 popup; onboarding, home, create-alias, fund, return, consent, settings, history, unlock and connect-approval screens all render with zero scroll at that size. — Manual-Chromium-tested (automated scrollWidth/Height assertions + screenshots).
- Separate full-page manager for complete history and recovery details. — Implemented.
- Cream/lilac/mint design, SVG mascot, generated avatars, bundled Nunito; reduced-motion respected. — Implemented, screenshots.
